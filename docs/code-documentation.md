# Документация в коде

## Зачем

Документация объясняет «почему», код — «что». Хороший комментарий отвечает
на вопрос, который не выводится из кода: зачем так, а не иначе, какие
ограничения, на что ссылается.

Плохой комментарий пересказывает код и устаревает быстрее, чем код меняется.
Такой комментарий хуже отсутствия комментария: он вводит в заблуждение.

## Что документируем

- **TSDoc на всех экспортируемых сущностях** (функции, типы, компоненты, хуки):
  что принимает, что возвращает, побочные эффекты, инварианты.
- **Комментарии «почему»** в неочевидных местах: обходные пути, магические числа,
  нетривиальные решения.
- **Формулы и регуляторика** — рядом с формулой, даже если «очевидно»
  (НДС, скидки, стоимость ножа = длина × 3 + 500).
- **Ссылки на тикеты/спеки** — если решение обсуждалось (`KOR-123`, `docs/...`).

## Чего НЕ делаем

- Пересказ кода (`// цикл по массиву`, `// возвращаем результат`).
- Закомментированный код — git помнит всё.
- `TODO` без контекста — только `TODO(TICKET): ...`.
- Устаревшие комментарии — хуже отсутствия.

## Форматы

- TSDoc: `/** ... */` над экспортируемой сущностью.
- Инвариант: `// invariant: ...` — короткая метка, легко грепается.
- TODO/FIXME: только с тикетом.
- Магическое число: либо `const NAME = 48; // почему именно 48`,
  либо `padding: 48 // было p: 6 в MUI (6 * 8px)`.

## Автоматика (планируется)

- `jsdoc/require-jsdoc` для новых экспортируемых сущностей — включим
  **после** того, как P0/P1 закрыты, чтобы не завалить baseline.
- Ручной проход по P0/P1 перед каждым релизом.

## Приоритеты

- **P0:** бизнес-логика (`calculatorApi`, `useCalculator`, `useLayout`, формулы).
- **P1:** публичные типы и API модулей (`features/*/index.ts`, `designTokens.ts`, `antdTheme.ts`).
- **P2:** нетривиальные хуки и компоненты (`LayoutSvg*`, `KnifePage` dropzone).
- **P3:** UI-компоненты и утилиты — по остаточному принципу.

## Правило для PR

Трогаешь файл — приводи доки в порядок **в этом же PR**, если правка
касается экспортируемой сущности. Отдельные «PR с доками» — только для
приоритизированного прохода P0/P1, не «весь проект».

## PowerShell-заметки (для команды)

- `git commit -F- <<'EOF' ... EOF` — это bash-синтаксис heredoc, в PowerShell
  **не работает**. Используй `git commit -F <временный_файл>` (создать файл
  с сообщением, передать, удалить) или `git commit -m "..."` (для коротких).
- `npm ci` может не уложиться в 30-секундный лимит инструмента (Cline);
  при таймауте — перезапуск в фоне с логом, потом проверка `npm ls <package>`.
- `core.autocrlf=true` + отсутствие `.gitattributes` → предупреждения
  `LF will be replaced by CRLF`. С `.gitattributes` (добавлен в PR #4)
  предупреждения уходят, в индексе всегда LF.

## Что это НЕ решает

- Не заменяет тесты. Документация объясняет «почему», тесты проверяют «что».
- Не заменяет README. README — для новых людей (как запустить, структура).
  Этот документ — для тех, кто уже пишет код (как комментировать).
- Не требует документировать всё сразу. P0/P1 — да, P2/P3 — по мере
  прикосновения.
